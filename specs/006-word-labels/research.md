# Research: Метки слов

Решения Phase 0. Каждое снимает неизвестное из Technical Context или фиксирует выбор,
от которого зависит модель данных и контракт.

## R1. Хранение меток: две новые таблицы

**Decision**: таблица `labels` (метка) и таблица-связка `word_labels`
(`word_id`, `label_id`, составной первичный ключ), обе с `ON DELETE CASCADE` на
родителя. Таблица `words` не меняется.

**Rationale**: связь «многие ко многим» (FR-001, FR-002) в реляционной базе — это
связка. Составной ключ сам гарантирует «не больше одного вхождения метки на слове».
Каскад на обоих концах даёт FR-014 (удаление метки снимает её со всех слов) и
FR-015 (удаление слова снимает его метки, метки остаются) без кода в сервисе.
`PRAGMA foreign_keys=ON` уже включается в `app/db.py` для каждого соединения,
включая тестовые. Миграция только создаёт таблицы — `batch_alter_table` не нужен,
внешние ключи `progress` и `review_log` не затрагиваются (Принцип IV).

**Alternatives considered**:
- Строка меток через разделитель в колонке `words.labels` — переименование и
  удаление метки превращаются в правку текста во всех строках, фильтр — в `LIKE`
  с ложными совпадениями («кухня» внутри «кухня-2»). Отвергнуто.
- JSON-массив в `words` — те же проблемы плюс нет внешнего ключа и уникальности.
- Хранить метки в `settings` key/value — это данные словаря, а не настройка.

## R2. Уникальность без учёта регистра: ключ, вычисленный в Python

**Decision**: у метки два поля — `name` (как ввели, обрезанное) и `name_key`
(`name.strip().casefold()`), уникальный индекс по `name_key`. Ключ считает Python
при создании и переименовании.

**Rationale**: метки русские, а встроенные в SQLite `lower()` и `COLLATE NOCASE`
понимают только ASCII: «Кухня» и «кухня» для них разные строки. Тот же приём уже
работает для слов (`word_key`). `casefold` вместо `lower` — на случай «ß» и прочих
особых случаев, бесплатно. Уникальный индекс — последняя линия обороны: роутер
проверяет конфликт заранее и отвечает 409 с человекочитаемым `detail`.

**Alternatives considered**: ICU-расширение SQLite для регистронезависимого
сравнения — новая зависимость ради одной колонки (Принцип V). Хранить только
`name` в нижнем регистре — теряет написание, которое ввёл пользователь.

## R3. Метки в форме слова: имена, а не идентификаторы

**Decision**: `POST /words` и `PATCH /words/{id}` принимают поле `labels` — список
**названий**. Сервер в той же транзакции, что и сохранение слова, находит
существующие метки по `name_key`, недостающие создаёт и заменяет набор меток слова
целиком. В `PATCH` отсутствие поля `labels` означает «не менять», пустой список —
«снять все».

**Rationale**: уточнение Q4 требует, чтобы метки менялись только вместе с правкой
слова и чтобы отменённая или отклонённая (409) правка не создавала новых меток
(FR-003a, FR-004a). Если бы фронт сначала создавал метку `POST /labels`, а потом
сохранял слово, отказ на втором шаге оставил бы висящую метку. Имена в одном
запросе делают операцию атомарной: `get_session` откатывает всю транзакцию на
любом исключении, включая 409 дубля. Проверка дубля (`_same_meaning`) идёт до
создания меток, так что откатывать на практике нечего.

Разрешение имён: пробелы по краям обрезаются, пустые строки — 422, повторы в
списке схлопываются по ключу, совпадение с существующей меткой по ключу берёт
существующую с её написанием (регистр введённого не перезаписывает метку —
переименование делается только на вкладке «Метки»).

**Alternatives considered**:
- Список `label_ids` + отдельное создание меток — неатомарно, см. выше.
- Отдельные маршруты `PUT/DELETE /words/{id}/labels/{label_id}` — это модель
  «правка прямо в строке» (вариант A в Q4), от которой отказались.

## R4. Отдача меток слова

**Decision**: `WordOut` получает поле `labels: list[LabelRef]` (`id`, `name`),
упорядоченное по названию без учёта регистра, «ё» = «е» (R6). Отношение `Word.labels`
грузится `lazy="selectin"`, как `progress`, с `order_by` по тому же ключу в SQL.
`resolve_labels` возвращает метки уже отсортированными: присвоенный `word.labels`
отдаётся в ответе на `POST`/`PATCH` как есть, а `order_by` связи действует только
при загрузке из базы.

**Rationale**: строка словаря показывает метки (FR-003), форма «Изменить»
заполняется ими, ответ `POST /words` сразу содержит метки. `selectin` — один
дополнительный запрос на страницу из 50 слов, без N+1. `WordOut` используется и в
занятии (`new_words`, `replacement`): лишнее поле там безвредно, а отдельная схема
ради его исключения — лишняя сложность. Фронт занятия поле не читает; метки в
занятиях не участвуют (Assumptions спеки).

## R5. Фильтр словаря: `label=<id>` или `label=none`

**Decision**: `GET /words` получает параметр `label`: целое число — слова с этой
меткой, строка `none` — слова без единой метки, иное — 422. Реализация —
`EXISTS` / `NOT EXISTS` по `word_labels`, условия складываются с `search`,
`status`, `priority` через AND (FR-007, FR-008, Q3). Неизвестный `id` — пустой
список, не 404: фильтр — запрос, а не адрес ресурса.

**Rationale**: один параметр отражает решение Q3 «одно значение за раз» и не даёт
передать противоречивое сочетание вроде `label_id=3&unlabeled=true`. По `id`, а не
по названию: переименование метки не должно ломать выбранный фильтр.

Индекс `ix_word_labels_label_id`: составной ключ `(word_id, label_id)` ускоряет
поиск меток слова, а для фильтра по метке нужен индекс, начинающийся с `label_id`.

**Alternatives considered**: два параметра `label_id` + `unlabeled: bool` —
допускают противоречие; фильтр по имени — ломается при переименовании.

## R6. Список меток: сортировка и счётчик в одном запросе

**Decision**: `GET /labels` — одна выборка `labels LEFT JOIN word_labels GROUP BY`
с `count(word_id)`, сортировка в Python по `label_sort_key(name_key)` (FR-009).

**Rationale**: `ORDER BY name` в SQLite сравнивает байты UTF-8, и порядок
кириллицы с латиницей и регистром будет неожиданным; `name_key` уже в нижнем
регистре. Ключ сортировки — `name_key` с заменой «ё» на «е» (`label_sort_key`):
иначе «ё» (U+0451) ушла бы после «я». Тот же порядок в SQL даёт
`func.replace(Label.name_key, "ё", "е")`: в UTF-8 «а–п» (`D0 B0…BF`) идут перед
«р–я» (`D1 80…8F`), поэтому побайтовое сравнение SQLite после замены совпадает с
алфавитом. Латиница идёт перед кириллицей и там и там. Меток десятки, сортировка в
памяти ничего не стоит. Счётчик нужен и для списка, и для текста подтверждения
удаления (FR-013) — отдельного маршрута «сколько слов у метки» не требуется.

**Alternatives considered**: сортировка на фронте — сервер тогда отдаёт
неупорядоченный список, а контракт FR-009 проверяется только глазами.

## R7. Длина и валидация названия

**Decision**: название — 1…50 символов после обрезки пробелов; проверка в Pydantic
одним валидатором для `LabelCreate`, `LabelUpdate` и элементов `labels` в
`WordCreate`/`WordUpdate`. Колонка `name` — `String(50)`. Предел — именованная
константа `LABEL_NAME_MAX` в `schemas.py` с комментарием «почему».

**Rationale**: закрывает оставшийся после уточнения пункт (Assumptions: «порядка
50 символов»). Это не параметр алгоритма, поэтому не `config.py`, а схема —
по аналогии с `max_length=128` у слова.

## R8. Переименование и регистр

**Decision**: `PATCH /labels/{id}` отвечает 409, если новый `name_key` занят
**другой** меткой. Совпадение ключа с самой меткой («кухня» → «Кухня») — правка
написания, разрешена (Edge Cases спеки).

## R9. Интерфейс: поле меток — свой компонент без библиотек

**Decision**: компонент `LabelPicker` — выбранные метки «чипами» с крестиком и
текстовое поле, под которым по мере ввода выпадают подходящие метки из
`GET /labels` (сравнение по `toLocaleLowerCase` по подстроке) и, если точного
совпадения нет, пункт «Создать метку «…»». Enter выбирает первый пункт. Компонент
встраивается в `WordForm`, поэтому одинаков в форме добавления и в «Изменить»
(FR-004, FR-004a).

**Rationale**: combobox из библиотеки — новая зависимость (Принцип V); нужное
поведение умещается в один компонент на `useState`. `<datalist>` не умеет
чипы и пункт «Создать».

## R10. Вкладка «Метки» в «Настройках»

**Decision**: страница «Настройки» получает переключатель вкладок: «Общие»
(нынешние секции «Порядок новых слов» и «Голос озвучки» без изменений) и
«Метки». Выбранная вкладка — в query-параметре `?tab=labels`, чтобы ссылка вела
прямо на неё и переживала перезагрузку. Вкладка «Метки» — компонент
`LabelsSection`: список с числом слов, поле «Новая метка», переименование прямо
в строке списка (поле + «Сохранить»/«Отмена»), удаление через `window.confirm`
с числом слов — тот же приём, что у удаления слова.

**Rationale**: решение Q1. Query-параметр вместо `localStorage` — вкладка это
навигация, а не предпочтение; react-router уже подключён.

## R11. Согласование кешей на фронте

**Decision**: ключ кеша `['labels']` для `GET /labels`. После сохранения или
удаления слова инвалидируются `['words']`, `['overview']` и `['labels']` (меняются
счётчики, могут появиться новые метки). После переименования или удаления метки —
`['labels']` и `['words']` (метка в строках словаря). Если метка, выбранная в
фильтре словаря, пропала из `['labels']`, фильтр сбрасывается на «Все метки»
(Edge Cases: «Фильтр по удалённой метке»).

## R12. Импорт

**Decision**: `app/cli.py` не меняется. Тест в `test_import.py` закрепляет, что
повторный импорт сохраняет связки `word_labels` существующей строки и не создаёт
меток (FR-016).

**Rationale**: импорт обновляет существующие строки на месте (сливает перевод), а
не пересоздаёт их, поэтому связки уцелеют — но это поведение нужно закрепить
тестом, а не надеждой (Принцип III).
