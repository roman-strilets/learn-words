## Phase 4: User Story 2 — Услышать голос до того, как выбрать его (Priority: P2)

видит причину, а не гадает

**Independent Test**: выбрать несколько голосов подряд и убедиться, что каждый
произносит образец сразу после нажатия, не открывая занятие

Вынести общее тело в helper, который использует и `speak()`, чтобы разбор ошибок и обход зависшей очереди не раздвоились. В комментарии объяснить, зачем метод существует: `setState` асинхронен, и `speak()` сразу после `selectVoice()` взял бы предыдущий голос (research.md, п. 3)
- [X] T014 [US2] В `frontend/src/speech/SpeechProvider.tsx` завести состояние `error: string | null` и выставлять его в `utterance.onerror` человекочитаемым текстом: `not-allowed` — озвучку запретил браузер, прочие коды — отказал выбранный голос. - [X] T015 [US2] В `frontend/src/pages/SettingsPage.tsx` завести именованную константу с образцом — короткая английская фраза, одна на все голоса — и вызывать `speakWith` в том же обработчике клика, что и `selectVoice`, передавая выбранный голос напрямую (для «Системного голоса» — `null`). ## Dependencies & Execution Order

### Phase Dependencies

- **Setup (Phase 1)**: зависимостей нет, начинается сразу
- **Foundational (Phase 2)**: после Setup. **Блокирует все истории** — контракт контекста меняется несовместимо
- **US1 (Phase 3)**: после Phase 2. Ни от каких историй не зависит
- **US2 (Phase 4)**: после Phase 2. Технически может идти параллельно US1, но T015 и T016 правят страницу, которую создаёт T010 — на практике удобнее после US1
- **US3 (Phase 5)**: после Phase 2 и после T010 (правит ту же страницу)
- **Polish (Phase 6)**: после всех историй, которые решено делать

### User Story Dependencies

- **US1 (P1)**: самостоятельна. Даёт законченную вкладку с выбором голоса — это MVP
- **US2 (P2)**: добавляет образец и сообщение об отказе. Провайдерная часть (T013, T014) независима от US1; страничная (T015, T016) требует созданной в T010 страницы
- **US3 (P3)**: только ветки пустого состояния на той же странице. Ничего из US1/US2 не ломает

### Within Each User Story

- Провайдер (`SpeechProvider.tsx`) — до страницы, которая его читает
- Страница — до маршрута и пункта навигации
- Контрольная точка истории — после всех её задач

### Parallel Opportunities

Их мало, и это честно: фича правит два файла, и почти все задачи ложатся в один
из них.

- Phase 1: T002 и T003 делаются в одном заходе в браузере
- Phase 2: T005 → T006 → T007 → T008 идут строго последовательно — один файл
- Phase 3–5: задачи внутри истории правят одну и ту же `SettingsPage.tsx`, параллелить нечего
- Phase 6: T019 (README) помечен `[P]` — единственная задача в другом файле, её можно писать, пока идут ручные проверки T020–T022

Если работают двое: после Phase 2 один берёт US1 (страница, маршрут, навигация),
второй — провайдерную часть US2 (T013, T014) в `SpeechProvider.tsx`. Дальше страничные
задачи сходятся в одном файле, и разделение перестаёт помогать.

## Implementation Strategy

### MVP First (User Story 1 Only)

1. Phase 1: Setup — зафиксировать исходное состояние
2. Phase 2: Foundational — привести контекст к новому контракту (**критично, блокирует всё**)
3. Phase 3: US1 — страница, выбор, маршрут
4. **ОСТАНОВИТЬСЯ И ПРОВЕРИТЬ**: шаги 1, 2, 4, 5 из quickstart.md
5. На этом вкладка уже полезна: голос выбирается и применяется

### Incremental Delivery

1. Setup + Foundational → контекст готов, видимых изменений нет
2. + US1 → вкладка работает → **MVP**
3. + US2 → выбор перестаёт быть вслепую: образец и объяснение отказа
4. + US3 → крайние случаи объяснены текстом
5. + Polish → README, ручные проверки, ворота, коммит

Каждая история добавляет ценность, не ломая предыдущую.
