# Research: Словарь фраз

Открытых вопросов в Technical Context нет: стек, хранилище и инструменты те же, что у
слов. Ниже — проектные решения, которые нужно было принять, прежде чем писать модель
данных и контракт.

## R1. Отдельные таблицы, а не колонка «вид записи»

**Decision**: пять новых таблиц — `phrases`, `phrase_progress`, `phrase_review_log`,
`phrase_labels`, `phrase_label_links`. Существующие таблицы слов не меняются.

**Rationale**: пользователь прямо просил «отдельную таблицу» и «не пересекаться со
словами». Отдельные таблицы дают это пересечение невозможным по построению: запрос
по `words` не может вернуть фразу, `finish` по `review_log` не может пересчитать фразу,
счётчики статистики слов не меняются (SC-002, SC-003). Внешние ключи и каскады
остаются простыми: `phrase_progress.phrase_id → phrases.id`, как у слов.

**Alternatives considered**:
- `words.kind` + общие `progress`/`review_log`: каждый из ~30 запросов слов пришлось
  бы дополнить фильтром по виду, и забытый фильтр незаметно смешал бы фразы со
  словами — ровно то, чего пользователь просил избежать. Плюс миграция живой таблицы
  `words` (Principle IV) ради пользы, которой нет.
- Общий `review_log` с nullable `phrase_id` и CHECK «ровно один из двух»: меньше
  таблиц, но та же проблема фильтров в статистике и `finish`, и пересборка
  `review_log` через `batch_alter_table` на базе с месяцами прогресса.

## R2. Один код для двух колод: описание колоды (`Deck`)

**Decision**: новый модуль `backend/app/decks.py` с замороженным dataclass `Deck`:
модели записи, прогресса, журнала, метки и таблица связки, параметры занятия из
`settings`, способ нормализации ответа, тексты ошибок («Слово не найдено» / «Фраза
не найдена»). Две константы — `WORDS` и `PHRASES`. Функции `study_service`,
`exercises` (дистракторы), `labels_service`, `word_filters` и роутеры принимают
`deck` параметром; для слов по умолчанию `WORDS`, поэтому вызовы и тесты слов не
меняются.

Чтобы общий код и общие Pydantic-схемы работали с обеими колодами без `getattr` по
строкам, у моделей фраз есть синонимы с именами слов (`sqlalchemy.orm.synonym`):
`Phrase.word → text`, `Phrase.word_key → text_key`, `PhraseProgress.word_id →
phrase_id`, `PhraseReviewLog.word_id → phrase_id`. Синонимы работают и в
`select()`/`where()`, и в `from_attributes`. Имена в базе остаются честными.

**Rationale**: алгоритм занятия (раунды, `finish`, оценка, дистракторы) — самое
хрупкое место проекта (Principle III). Копия `study_service` для фраз означала бы
две версии одной логики, которые разойдутся при первой правке. Описание колоды —
минимальная абстракция под реальную, уже существующую вторую колоду (Principle V).

**Alternatives considered**:
- Скопировать сервисы и роутеры под фразы: быстро, но каждое будущее изменение
  правил занятия нужно делать дважды и дважды тестировать.
- Абстрактный базовый класс моделей с общими колонками (`__abstract__`-миксин):
  имена колонок у слов (`word_id`) уже в базе, переименование — миграция живых
  таблиц; синонимы решают ту же задачу без миграции.
- Переименовать в API `word_id` → `item_id`: ломает контракт слов и фронтенд целиком
  ради косметики.

## R3. Форма API: те же схемы, отдельные префиксы

**Decision**: фразы отвечают теми же схемами, что слова (`WordOut`,
`WordWithProgress`, `SessionOut`, `ExerciseRound`, `StatsOverview`, `LabelOut` …), а
маршруты живут под своими префиксами: `/api/phrases`, `/api/phrase-labels`,
`/api/phrase-study`, `/api/phrase-stats`. Роутеры строятся фабрикой
`make_*_router(deck)` из тех же функций, что и роутеры слов. В ответах для фраз поле
`word` — текст фразы, `word_id` — id фразы, `word_count` у метки — число фраз.

**Rationale**: фронтенд целиком переиспользует раннер раундов, карточки упражнений,
форму, строку словаря и раздел меток — меняется только префикс клиента. Маршруты
слов не меняются ни на байт (SC-003). Отдельный префикс, а не параметр `?deck=`,
делает невозможным случайно забыть параметр и попасть в слова.

**Alternatives considered**:
- Параметр `deck` в каждом запросе `/study/*`: меняет тела запросов слов, а забытый
  параметр молча уходит в колоду слов.
- Отдельные схемы с `phrase`/`phrase_id`: честнее по именам, но удваивает
  `types.ts`, раннер и карточки на фронте без пользы для пользователя.
- `/api/phrases/labels`, `/api/phrases/study/*`: пересекается с `/api/phrases/{id}`
  и зависит от порядка регистрации маршрутов.

## R4. Сравнение ответа по фразе

**Decision**: `normalize_answer` получает флаг `drop_apostrophes`; колода фраз
включает его. Апостроф удаляется (не заменяется пробелом): «It's up to you.» и
«Its up to you» дают `its up to you`. Остальные правила общие: регистр, лишние
пробелы, дефисы, пунктуация и ведущие `to`/`a`/`an`/`the`. Состав и порядок слов
сравниваются строго.

**Rationale**: FR-020 и SC-005 прямо требуют игнорировать апостроф, а пользователь
пишет фразы с телефона и ноутбука, где апострофы разные или их лень ставить. Для
слов апостроф остаётся значимым (`o'clock`) — их поведение не трогаем.

**Alternatives considered**: нечёткое сравнение (Левенштейн ≤ 1) — засчитало бы
пропущенную букву в слове фразы, а спецификация требует, чтобы ошибка в слове не
засчитывалась.

## R5. Варианты ответа из маленького словаря фраз

**Decision**: тот же `pick_distractor_words`, параметризованный колодой. Он уже
добирает случайные записи, если похожих мало, и возвращает меньше вариантов, если
записей не хватает. Карточка с 2–3 вариантами (или с одним — правильным, если
фраза в словаре одна) остаётся решаемой. Фронтовая `ChoiceCard` рисует
`options.map`, горячие клавиши 1–4 работают на любое число вариантов ≤ 4.

**Rationale**: в словаре слов 7000 записей, и путь «вариантов меньше четырёх» там не
встречался; у фраз он будет обычным в первые дни. Нужны тесты на 1, 2 и 3 фразы в
словаре.

## R6. Сборка из букв для фраз

**Decision**: без изменений алгоритма: `build_mask` оставляет пробелы, апострофы и
знаки фиксированными разделителями, в банк идут только буквы и цифры
(«It's up to you!» → маска `__'_ __ __ ___!`, 10 букв). Проверка сравнивает
нормализованный текст, как для слов.

**Rationale**: пользователь выбрал вариант «из букв, как у слов» (Q1: B); слова из
нескольких частей (`roll out`) уже идут этим путём.

## R7. Лимиты и порядок новых фраз

**Decision**: три новых параметра в `app/config.py`: `new_phrases_per_session = 5`,
`review_phrases_per_session = 5`, `daily_new_phrases_limit = 20`. Дневной лимит
считается по `phrase_progress.started_at`. Новые фразы всегда идут по возрастанию
`id`, отмеченные «Учить первой» — раньше; настройка `new_words_order` к фразам не
применяется.

**Rationale**: FR-016 — лимиты раздельны; Principle II — числа только в конфиге.
Отдельная настройка порядка для фраз в спецификацию не вошла (YAGNI).

## R8. Метки фраз

**Decision**: свои таблицы `phrase_labels` (те же поля, что `labels`: `name`,
`name_key`, `description`, уникальный `name_key`) и связка `phrase_label_links`.
`labels_service` (ключ названия, порядок «ё» = «е», `resolve_labels`) принимает
модель метки из колоды. Роутер меток фраз — без `POST /classify`: автоматическая
разметка фраз вне объёма. На фронте `LabelsSection` и `LabelPicker` получают
клиент колоды; вкладка настроек `/settings?tab=phrase-labels`.

**Rationale**: пользователь выбрал отдельные метки (Q2: C). Поле `description`
оставлено ради единой схемы `LabelOut` и чтобы будущая разметка фраз не требовала
миграции, хотя сейчас его читает только интерфейс.

## R9. Фронтенд: колода как параметр

**Decision**: `api/client.ts` получает `deckApi(deck)` — тот же набор методов
словаря, меток, занятия и статистики с префиксом колоды; нынешние методы `api.*`
остаются как `deckApi('words')`. Ключи запросов TanStack Query начинаются с колоды
(`['phrases', …]`, `['phrase-labels']`, `['overview', 'phrases']`). Маршруты:
`/phrases`, `/phrases/new`, `/study?deck=phrases&mode=learn|review` (без `deck` —
слова, как сейчас). Компоненты словаря выносятся из `WordsPage` в общие с пропом
`deck`; панель автоматической разметки остаётся только у слов.

**Rationale**: максимальное переиспользование без второго раннера; старые ссылки
`/study?mode=…` продолжают работать.
