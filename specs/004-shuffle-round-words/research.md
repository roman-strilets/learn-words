# Research: Случайный порядок слов в каждом раунде

## Исходное состояние

`study_service._rounds_for` строит все четыре раунда одним списочным выражением по одному
и тому же `words`. Поэтому порядок слов во всех раундах совпадает с порядком отбора:
в повторении это «самые просроченные первыми», в изучении — `word_ids` в порядке знакомства.
`RoundsRunner` берёт `rounds[next].exercises` как есть, только отфильтровав выбывшие слова.
Существующие тесты проходят раунды по `word_id`, а не по позиции, поэтому от порядка
они не зависят.

---

## R1. Где выбирать порядок

**Decision**: Порядок каждого раунда выбирает сервер при сборке плана
(`_rounds_for`, общий для `GET /study/session?mode=review` и `POST /study/rounds`).
Фронт на границе раунда только поправляет порядок, если его нарушила информация,
которой у сервера не было (R3).

**Rationale**: Генерация упражнений покрыта pytest (Принцип III), а у фронта
тест-раннера нет. Перемешивание на сервере покрывает FR-001, FR-002, FR-003, FR-006
и FR-004 для занятия без ошибок. Состояния на сервере не появляется: план по-прежнему
собирается за один запрос и отдаётся целиком (Принцип I).

**Alternatives considered**:
- *Перемешивать только на фронте*: основная логика осталась бы без тестов.
  Отклонено.
- *Спрашивать у сервера порядок на каждой границе раунда*: лишние запросы, а серверу
  пришлось бы передавать «что было показано последним». Выигрыша это не даёт. Отклонено.

## R2. Алгоритм порядка раунда

**Decision**: Чистая функция `order_round(items, previous, last, rng)` в `app/exercises.py`:

1. `candidate = items` в порядке `rng.shuffle`.
2. Если `len < 2` — вернуть как есть.
3. Из кандидатов `[candidate, swap(0,1), rotate_left(1), swap(1,2)]` взять первый, который:
   - не равен `previous` (FR-003);
   - при `len ≥ 3` не начинается с `last` (FR-004).
4. При `len == 2` проверяется только первое условие (FR-005).

Сервер вызывает функцию для раундов 2–4: `previous` — порядок предыдущего раунда,
`last` — его последний элемент. Первый раунд — чистый `shuffle`.

**Почему кандидатов всегда хватает** (`n ≥ 3`, `x = last`, `P = previous`,
`q` — перемешанный порядок):
- `q[0] == x`: у `swap(0,1)` и `rotate_left` первым идёт `q[1] ≠ x`. Эти два порядка
  различны, поэтому совпасть с `P` может не больше одного из них.
- `q[0] ≠ x`, но `q == P`: `swap(1,2)` сохраняет первым `q[0]` и отличается от `q`,
  а значит и от `P`.
- `n == 2`: есть всего два порядка, и `swap(0,1)` — второй из них.

Функция детерминирована при заданном `rng`, поэтому тесты задают семя.

**Rationale**: Нужны гарантии «всегда», а не «почти всегда» (SC-001, SC-002). Если
тянуть перемешивания до удачи, цикл придётся ограничивать, а для исхода «не
повезло» всё равно понадобится запасной путь. Здесь запасной путь и есть весь
алгоритм. Первый раунд без ограничений перемешан равномерно, этого хватает для SC-003.
У раундов 2–4 распределение чуть смещено, но спека требует только отличия
от предыдущего раунда.

**Alternatives considered**:
- *Просто `rng.shuffle` на каждый раунд*: при 2 словах порядок совпадает
  в 50 % случаев, при 5 — в 0,8 %. Нарушает SC-001. Отклонено.
- *Сдвиг порядка на фиксированный шаг*: предсказуемо, а спека требует
  «произвольный». Отклонено.

Функция обобщённая (`Sequence[T]`, сравнение по ключу), чтобы тестировать её
на числах, а не на ORM-объектах.

## R3. Стык раундов после повтора

**Decision**: На границе раунда `RoundsRunner` применяет к следующему раунду ту же
процедуру кандидатов (без перемешивания), чистой функцией
`arrangeRound(items, previous, lastWordId)` в `frontend/src/lib/roundOrder.ts`.
- `previous` — порядок первых показов предыдущего раунда (как его показали,
  без выбывших слов);
- `lastWordId` — слово последней отвеченной карточки;
- следующий раунд сначала фильтруется от выбывших слов.

**Rationale**: Сервер знает только запланированный конец раунда. Если раунд
закончился повтором после ошибки, последним показано другое слово, и FR-004 может
нарушиться. Кроме того, выбывшее слово может сделать два разных серверных порядка
одинаковыми после фильтрации (`[a,b,c]` и `[a,c,b]` без `c`). Это нарушило бы FR-003.
Если план не менялся, функция возвращает его как есть, и в обычном занятии порядок
остаётся серверным.

Функция из четырёх кандидатов проверяется `yarn typecheck`, `yarn build` и сценариями
в [quickstart.md](./quickstart.md). Тот же алгоритм покрыт pytest на стороне сервера.

**Alternatives considered**:
- *Не чинить стык после повтора*: нарушает FR-004 и US2, сценарий 2. Отклонено.
- *Переставлять повтор не в конец раунда*: противоречит FR-008. Отклонено.

---

## R4. Порядок и повторы после ошибки

**Decision**: Не меняется. Повтор после ошибки, как и сейчас, встаёт в конец текущей
очереди (`advance` в `RoundsRunner`). В сравнение порядков идут только первые показы.

**Rationale**: FR-008 и определение «порядка слов раунда» в спеке.

---

## R5. Контракт API

**Decision**: Схема ответа не меняется. Меняется только смысл порядка:
`rounds[i].exercises` теперь перемешан для каждого раунда с гарантиями R2.
Правки `schemas.py` и `types.ts` не нужны. Раздел README про раунды и API
обновляется (Принцип V).
