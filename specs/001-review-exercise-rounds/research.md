# Phase 0 — Research: Повторение раундами по типам упражнений

**Feature**: [spec.md](./spec.md) | **Date**: 2026-08-29

Все пункты Technical Context закрыты: NEEDS CLARIFICATION не осталось. Ниже —
решения, которые задают форму реализации, с отвергнутыми альтернативами.

---

## D-1. Где строится план раундов

**Decision**: план раундов строит сервер и отдаёт целиком в ответе
`GET /api/study/session?mode=review`; порядок показа карточек и повторы после ошибок
ведёт фронт.

**Rationale**: упражнения нельзя собрать без базы (дистракторы подбираются запросами
по `word_key` и расстоянию Левенштейна), поэтому генерация обязана быть серверной.
Очередь же по конституции (Принцип I) живёт на фронте, и сервер не имеет права
помнить занятие между запросами. Разделение «сервер даёт материал, клиент ведёт
очередь» повторяет то, как уже устроен режим «Изучение».

**Alternatives considered**:
- *Отдавать по одному раунду за запрос (`POST /study/exercises`)* — меньше данных
  за раз, но появляется лишний эндпоинт и по одному круговому запросу на каждый
  раунд ради экономии нескольких килобайт. Отвергнуто как усложнение без причины.
- *Хранить план на сервере* — прямо запрещено Принципом I.

---

## D-2. Когда пересчитывается расписание

**Decision**: во время занятия ответы только проверяются и логируются; расписание
слова обновляется один раз — на `POST /api/study/review/finish`.

**Rationale**: слово теперь получает четыре упражнения за занятие. Если оставить
текущий вызов `apply_answer` на каждый ответ, безошибочное занятие умножит интервал
на `ease` четырежды, а первая же ошибка переведёт слово в `learning` посреди занятия
и сломает раунды (FR-013a). Одно обновление в конце сохраняет прежнюю скорость роста
интервалов (SC-005).

**Alternatives considered**:
- *Двигать интервал только в последнем раунде* — привязывает правило расписания к
  порядку типов упражнений; смена порядка молча сломает расписание.
- *Оставить SM-2 на каждый ответ* — прямо противоречит FR-013 и SC-005.

## D-3. Как сервер узнаёт итог занятия, оставаясь stateless

**Decision**: занятие получает `session_id` (UUID, выдаёт сервер при сборке занятия);
клиент присылает его с каждым ответом, сервер пишет его в `review_log.session_id`.
На `finish` сервер группирует строки журнала по `session_id` и сам определяет:
слово прошло все четыре раунда, если по каждому из четырёх типов есть строка с
`correct = true`; ошибка была, если есть хотя бы одна строка с `correct = false`.

**Rationale**: итоговое качество остаётся серверным выводом из журнала, а не
присланным клиентом числом — это то, чего требует Принцип I. `session_id` не создаёт
серверного состояния: таблицы сессий нет, это ключ корреляции внутри уже существующего
журнала. Заодно журнал становится пригодным для статистики «сколько занятий и с каким
результатом».

**Alternatives considered**:
- *Клиент присылает `had_error: bool`* — оценку ответа начинает считать клиент,
  прямое нарушение Принципа I.
- *Границей занятия считать `progress.updated_at`* — не требует миграции, но попытки
  из брошенного вчера занятия протекут в сегодняшнее и превратят чистое занятие в
  «забытое» слово, что противоречит FR-017a.
- *Отдельная таблица сессий* — серверное состояние, запрещено.

## D-4. Что происходит с колонкой `session_id` в существующих данных

**Decision**: nullable-колонка `String(36)` с индексом; строки, накопленные до
доработки, остаются с `NULL` и продолжают участвовать в статистике.

**Rationale**: добавление колонки в SQLite выполняется `ALTER TABLE ADD COLUMN` без
пересоздания таблицы, поэтому внешние ключи `review_log → words` не двигаются —
ровно та ловушка, о которой предупреждает Принцип IV. `downgrade` делает
`op.drop_column` напрямую (SQLite ≥ 3.35 это поддерживает) и не использует
`batch_alter_table`.

**Alternatives considered**:
- *`NOT NULL` с заполнением задним числом* — потребовало бы выдумать идентификаторы
  для прошлых занятий; ложные данные хуже пустых.
- *Обойтись без колонки* — см. D-3, ломает FR-017a.

## D-5. Как собирается карточка для повтора после ошибки

**Decision**: повтор строится тем же `build_exercise(...)` с тем же типом, но с
увеличенным `attempt`; готовая карточка возвращается прямо в `AnswerResponse.next_exercise`.

**Rationale**: `build_exercise` уже принимает `attempt` и разводит по нему порядок
букв через `_stable_rng(word_id, attempt)`, а варианты выбора пересобираются на новом
`rng`. То есть FR-006a выполняется без новых функций. Отдача карточки прямо в ответе
избавляет от лишнего запроса на каждую ошибку и повторяет уже существующее поле
`next_exercise`.

**Alternatives considered**:
- *Повторять ту же карточку* — пользователь запоминает позицию кнопки, и «исправление»
  ошибки перестаёт что-либо значить (прямо отвергнуто в уточнениях спецификации).
- *Отдельный запрос за повторной карточкой* — лишний круговой запрос на каждую ошибку.

## D-6. Значение поля `attempt` в запросе ответа

**Decision**: `attempt` — номер показа слова в текущем раунде (1, 2, 3…), со сменой
раунда счёт начинается заново. Карточка со сборкой из букв, которая сейчас шлёт
`attempt = 2` при промахах, продолжает это делать: клиент отправляет
`max(номер показа, промахи ? 2 : 1)`.

**Rationale**: у обоих значений один смысл — «взято не с первой попытки», и они
согласованно снижают качество в `derive_quality`. Это позволяет выполнить FR-012a,
не добавляя в контракт ещё одно поле и не трогая `derive_quality`.

**Alternatives considered**:
- *Отдельное поле `round_attempt` и колонка под него* — вторая колонка ради нюанса
  журнала; не оправдано (Принцип V).
- *Считать каждый показ первой попыткой* — повторы стали бы неотличимы в журнале,
  прямо отвергнуто в уточнениях.

## D-7. Как режим ответа попадает на сервер

**Decision**: `AnswerRequest` получает `mode: SessionMode = learn` и
`session_id: str | None`. При `mode = review` `session_id` обязателен (иначе 422),
расписание не трогается, а в журнал пишется `session_id`. При `mode = learn` поведение
не меняется совсем (FR-018).

**Rationale**: явное поле честнее, чем вывод режима из наличия `session_id`, и
оставляет режим «Изучение» нетронутым без ветвлений «а вдруг».

**Alternatives considered**:
- *Отдельный эндпоинт `POST /study/review/answer`* — дублирует проверку ответа и
  логирование ради одного флага.
- *Выводить режим из наличия `session_id`* — неявная связь, которую придётся
  вспоминать при каждом чтении кода.

## D-8. Порядок раундов как доменная константа

**Decision**: `REVIEW_ROUNDS: tuple[ExerciseType, ...]` в `srs.py`; веса и
`pick_review_exercise` удаляются вместе с `REVIEW_EXERCISES`.

**Rationale**: порядок фиксирован спецификацией (FR-004) и настройкой не является,
поэтому ему место рядом с `LEARNING_STEPS` — там же, где живёт вторая такая же
последовательность. Числовые параметры расписания по-прежнему остаются в `config.py`,
как требует Принцип II; тип упражнения — не число, а доменная константа.

**Alternatives considered**:
- *Порядок в `config.py` / `.env`* — настройка, которой никто не пользуется (YAGNI),
  и валидация списка типов в env-строке.
- *Оставить взвешенный случайный выбор* — противоречит FR-002 и FR-004.

## D-9. Раннер занятия на фронте

**Decision**: новый компонент `ReviewSession.tsx` ведёт раунды; `StudySession.tsx`
остаётся раннером режима «Изучение»; общий переключатель карточек выносится в
`components/exercises/ExerciseView.tsx`.

**Rationale**: у режимов теперь разные правила очереди (список знакомства + вставка
через три карточки против раундов с повторами в конец). Ветвление по режиму внутри
одного компонента сделало бы обе логики нечитаемыми и поставило бы под удар FR-018.
Общего у них ровно одно — рендер карточки по типу упражнения, его и выносим.

**Alternatives considered**:
- *Один компонент с флагом режима* — два набора состояний в одном файле; риск задеть
  режим «Изучение».
- *Полностью независимая копия карточек* — дублирование `ExerciseView` без причины.
